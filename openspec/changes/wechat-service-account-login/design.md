# 微信服务号扫码登录技术设计

## 登录链路

1. 前端请求二维码，服务端从微信获取带缓存的 access token，并创建字符串场景二维码。
2. 服务端以二维码 ID 为键保存等待状态和五分钟过期时间，前端每两秒查询一次。
3. 微信向回调接口推送 `subscribe` 或 `SCAN` XML 事件；控制器先校验签名，再交给服务更新状态。
4. 首次观察到已确认状态时，服务端按 OpenID 原子查找或创建用户并签发 JWT，随后消费二维码状态。
5. 前端保存用户与 JWT，停止轮询并返回登录前页面。

## 配置与外部边界

- AppID、AppSecret 和回调 Token 只从服务端环境变量读取。
- access token 缓存在进程内，并在微信过期时间前提前失效；并发刷新复用同一个 Promise。
- 二维码状态只在进程内保存，适合当前单实例实现；多实例生产部署前需迁移到 Redis 等共享存储。
- 菜单地址和临时素材图片路径由环境变量提供，代码不硬编码外部域名或本机绝对路径。

## 安全边界

- 微信握手与事件回调均使用 SHA-1 规则校验 `signature`、`timestamp` 和 `nonce`。
- XML 回复对 CDATA 结束标记进行转义，避免动态值破坏消息结构。
- 菜单管理是远端写操作，要求有效 JWT 且实时查询数据库确认 `admin` 角色。
- 日志不输出 AppSecret、access token、完整 JWT 或未脱敏的配置。
- 本切片支持微信明文消息模式；兼容/安全模式的 AES 消息加解密不在本次范围内。

## 用户一致性

- OpenID 依赖现有稀疏唯一索引。
- 新用户使用 upsert 建立，处理并发扫码时的唯一键竞争。
- 新微信用户获得产品配置的 20 旺旺币，已有用户只补齐微信绑定状态和最近登录时间。
- JWT 使用现有策略识别的 `userId` 字段，并包含用户名和可选邮箱。

## 验证边界

- 单元测试模拟微信 HTTP、用户模型和 JWT，覆盖配置、签名、二维码状态、过期、登录和菜单授权。
- 服务端构建验证 NestJS 注入、类型和打包结构；前端构建验证 Nuxt 组件与 API 集成。
- 本地验证不会调用微信、上传素材、改变菜单，也不能证明真实扫码回调、公众号权限或公网网络可用。
